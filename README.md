# MyBand.video

Music intelligence platform: upload audio, get **BPM, key, chords, MIDI and song
sections** back.

The workspace, toolchain and environment strategy are in place, authentication
(Google, email, protected dashboard) is implemented, and the database - seven
tables, row level security and the analysis queue seam - is versioned as Supabase
migrations. Audio analysis itself is not built yet.

## Stack

| Layer    | Choice                                                      |
| -------- | ----------------------------------------------------------- |
| Frontend | Next.js 15 (App Router), TypeScript, Tailwind v4, shadcn/ui |
| Backend  | FastAPI (Python 3.12), Pydantic v2, psycopg                 |
| Database | PostgreSQL (Supabase)                                       |
| Storage  | Cloudflare R2 (S3-compatible, via boto3)                    |
| Compute  | RunPod GPU workers (audio analysis)                         |
| Monorepo | pnpm workspace, ESLint 9 flat config, Prettier, uv (Python) |

## Prerequisites

- **Node.js** >= 22.14 (`node -v`)
- **pnpm** 12.10.1 - pinned via the `packageManager` field:
  `corepack enable pnpm` (or `npm i -g pnpm@12.10.1` if Corepack is unavailable)
- **Python** >= 3.12 and **uv** (`uv --version`) for `apps/api`

## Setup

```bash
pnpm install                                  # JS workspace
cp apps/web/.env.example apps/web/.env.local  # web env (git-ignored)
```

## Environment variables

- **One `.env` per app, never at the repo root.** `apps/web/.env.local` (Next.js
  loads `.env.local`) and `apps/api/.env` (loaded by pydantic-settings).
- **Only `*.env.example` files are committed.** `.gitignore` ignores `.env` and
  `.env.*` while explicitly keeping `.env.example`, so secrets cannot leak and
  onboarding stays copy-paste.
- **Two namespaces, two audiences.**
  - `NEXT_PUBLIC_*` is inlined into the browser bundle, so it is public by
    definition: the API base URL and the Supabase publishable key. A real secret
    here is a leak, so the Supabase service-role key and all other credentials
    stay server-side (`apps/api`, server-only variables).
  - Everything else is server-only: `API_BASE_URL` for server-side fetches in
    `apps/web`, and all credentials in `apps/api`.
- **Third-party credentials keep canonical names** (`DATABASE_URL`, `R2_*`,
  `SUPABASE_*`, `RUNPOD_*`); our own settings use a `MYBAND_` prefix
  (`MYBAND_ENV`, `MYBAND_CORS_ORIGINS`). This keeps SDK expectations intact and
  makes it obvious which variables we own.
- Validation is fail-closed once code lands: Pydantic Settings rejects a
  missing/invalid `DATABASE_URL` at startup and web-side env reads are parsed
  with Zod, so a misconfigured environment fails at boot instead of at request
  time.

## Authentication

Supabase Auth owns identity and sessions; the app only decides who may see what.
Google and email/password sign-in, server-side session validation, middleware
protection and logout are implemented.

| Piece                        | Responsibility                                                               |
| ---------------------------- | ---------------------------------------------------------------------------- |
| `apps/web/middleware.ts`     | Next.js entry point; delegates to the session updater                        |
| `lib/supabase/middleware.ts` | Refreshes the session and enforces route protection on every matched request |
| `lib/supabase/server.ts`     | Cookie-backed Supabase client for Server Components, Actions, Route Handlers |
| `lib/supabase/env.ts`        | Zod-validated `NEXT_PUBLIC_SUPABASE_*` reads (fail-closed, parsed lazily)    |
| `features/auth/schemas.ts`   | Zod schemas for `FormData`, JWT claims and redirect targets                  |
| `features/auth/actions.ts`   | Server Actions: email sign-in/sign-up, Google OAuth, logout                  |
| `features/auth/session.ts`   | `getIdentity()` / `requireIdentity()` - verified server-side identity        |
| `features/auth/components/*` | Login form, Google button, logout button, inline feedback                    |
| `app/login/page.tsx`         | Email + Google sign-in (public)                                              |
| `app/auth/callback/route.ts` | Exchanges the OAuth/confirmation code for a session                          |
| `app/dashboard/page.tsx`     | Protected page (`requireIdentity`) - reference for future protected routes   |

Decisions worth knowing:

- **Sessions live in cookies**, written by `@supabase/ssr`, so the server can read
  them on the next request. The client is created per request and never cached in
  a module variable: a shared instance would leak one user's session to another.
- **Identity is verified with `getClaims()`**, which validates the access-token
  signature (locally against cached JWKS for projects on asymmetric signing keys,
  via the Auth server for symmetric ones) and refreshes the session when the token
  is near expiry. `getUser()` is the alternative when the freshest user record
  matters, at the cost of a network round trip. `getSession()` is never used for
  authorization: it reads the cookie without revalidating it, and the cookie is
  attacker-controlled.
- **Protection is default-deny.** `PUBLIC_PATHS` in `lib/supabase/middleware.ts`
  lists what is open (`/`, `/login`, `/auth/callback`); everything else requires a
  session, so a forgotten route fails closed. Add public assets (`robots.txt`,
  audio previews) to that set or to the matcher.
- **Middleware is not the authorization boundary.** Every protected page calls
  `requireIdentity()` again; a middleware regression must not be enough to expose
  a page (see CVE-2025-29927).
- **The browser's Supabase client reads the session and nothing else.** It exists so
  the uploader can send the user's access token to `apps/api` (`lib/supabase/client.ts`);
  every screen and every write still goes through a Server Action or the API, and no
  Supabase table is reachable from a page. Sign-in, sign-up, OAuth and logout remain
  Server Actions, so the browser still holds no key of its own.
- **Responses that write session cookies are `private, no-store`**, and the cache
  headers Supabase returns alongside refreshed cookies are forwarded, so a CDN
  cannot cache one user's session and serve it to the next visitor.
- **Redirect targets are validated** (`safeRedirectPath`) to same-origin relative
  paths, which blocks the `//evil.com` open-redirect trick on `?next=`.

### Supabase project setup

1. **Authentication → Providers → Email**: enabled by default. With "Confirm
   email" on, sign-up returns no session and the form shows a "check your inbox"
   notice; with it off the user is signed in immediately. Both paths are handled.
2. **Authentication → Providers → Google**: add the client ID/secret from Google
   Cloud Console, and register
   `https://<project-ref>.supabase.co/auth/v1/callback` as an authorized redirect
   URI in Google.
3. **Authentication → URL Configuration**: Site URL `http://localhost:3000` and
   redirect URLs `http://localhost:3000/auth/callback` plus every deployed origin
   (preview deployments included). URLs that are not listed are rejected.
4. Copy the Project URL and publishable key into `apps/web/.env.local`.

## Upload to analysis

A signed-in user drags an MP3 or WAV onto the dashboard and gets a song plus a
queued analysis job. `docs/upload-flow.md` holds the sequence diagram, the endpoint
contracts and the error table; this is the shape of it:

| Piece                                | Responsibility                                                         |
| ------------------------------------ | ---------------------------------------------------------------------- |
| `app/api/routes/uploads.py`          | `POST /uploads/presign`, `POST /uploads/complete`, `GET /uploads/{id}` |
| `app/api/routes/songs.py`            | `GET /songs` (the library) and `GET /songs/{id}`                       |
| `app/api/routes/jobs.py`             | `GET /jobs/{id}`                                                       |
| `app/services/uploads.py`            | The lifecycle rules: what may be uploaded, and what it becomes         |
| `app/services/storage.py`            | R2 (S3) access - presigning and HEAD - behind a protocol               |
| `app/core/auth.py`                   | Token verification: JWKS for asymmetric keys, the secret for HS256     |
| `features/uploads/components/*`      | The dropzone, the progress bar, the library list                       |
| `features/uploads/client-api.ts`     | Presign and complete, from the browser                                 |
| `features/uploads/put-to-storage.ts` | The XHR PUT to storage - the only reason this app uses XHR             |
| `features/uploads/server-api.ts`     | The library, read while the dashboard renders                          |

Decisions worth knowing:

- **FastAPI never receives audio.** The API writes a `pending` row, signs a PUT for
  exactly that one key, and the browser uploads straight to storage. Completion then
  asks the bucket what actually landed (`HEAD`) instead of believing the client,
  which is what makes the size and MIME rules real rather than advisory.
- **Completion is one transaction.** The upload's compare-and-swap, the song, the
  claim (`uploads_claim_key`) and the queued job commit together, so there is no song
  without a job and no claimed upload without a song. Completing the same upload
  twice answers `200` with the first result rather than creating a second song.
- **The browser's checks are a courtesy.** `features/uploads/file-rules.ts` mirrors
  the API's rules so a 3 GB FLAC is refused before it is sent; the API re-checks
  every rule against the object.
- **One error shape** - `{"detail": {"code", "message"}}`, FastAPI's own 422
  included - so the UI has one thing to render and one field to branch on.

## Database

The schema lives in `supabase/migrations` and is applied by `supabase db reset`,
which also loads `supabase/seed.sql`: a demo account (`demo@myband.local` /
`password123`) with projects, songs, jobs, results and a pending storage cleanup.
`docs/schema.md` explains the tables, the indexes and the RLS matrix; the schema
test suite in `apps/api/tests` asserts the same properties against a real database.

The CLI is deliberately **not** a dependency of this repository - run it with `pnpm
dlx supabase@latest <command>`.

```bash
pnpm dlx supabase@latest start      # 54322 Postgres, 54321 Data API, 54323 Studio
pnpm dlx supabase@latest db reset   # re-apply migrations + seed
pnpm dlx supabase@latest db lint --level warning
pnpm dlx supabase@latest stop
```

The database tests need a migrated database and skip themselves without one:

```bash
$env:MYBAND_TEST_DATABASE_URL = "postgresql://postgres:postgres@127.0.0.1:54322/postgres"
pnpm test:api
```

Rules that are not negotiable:

- **Migrations are the only way the schema changes.** Never in the dashboard SQL
  editor and never by hand on a running database - the two cannot be reconciled
  afterwards.
- **Never edit a migration that has been applied anywhere but locally.** Add a new
  one instead. `db reset` replays the whole list from scratch, so a mistake shows
  up immediately rather than in production.
- **Ids come from the application** (UUIDv7, `app/core/ids.py`). Do not add
  `default gen_random_uuid()` to a table.
- **Grants are explicit, and column-level where a row is only partly writable.** A
  new table in `public` is reachable through the Data API only if a migration
  grants it - pinned locally by `auto_expose_new_tables = false` in
  `supabase/config.toml`, and to be set the same on the cloud project.
- **Deletes are soft deletes** performed by the API, which is also the only writer:
  no table has a DELETE or INSERT policy, and `deleted_at` is not a column a
  browser session may write.

## Conventions

- TypeScript is strict (`strict`, `noUncheckedIndexedAccess`,
  `verbatimModuleSyntax`) via `tsconfig.base.json`; Next.js adds only its own
  `jsx`/`lib`/`paths` overrides.
- `@myband/shared` is a **source-only internal package** (`exports` points at
  `src/index.ts`) consumed through `transpilePackages` - no build/watch step and
  no stale `dist/`.
- Python cannot import TypeScript, so `packages/shared` is the client-side
  contract and FastAPI's Pydantic models are its mirror. Code generation from
  the OpenAPI schema is deliberately deferred until the duplication costs
  something.
- ESLint configs are per-package, composed from the root base config, and are
  run per package (`pnpm -r lint`) because ESLint 9 resolves flat config from
  the working directory.
- Next.js is pinned to `^15.5.27` even though 16.x is published - upgrading is a
  deliberate, separate change.

## Not implemented yet

Audio analysis itself: the RunPod dispatcher and its workers, the artifact contracts
(BPM, key, chords, MIDI, song sections) and the screens that read them. The
database, the queue state machine (`app/services/queue.py`), the job contract and the
whole upload lifecycle (`docs/upload-flow.md`) are implemented and tested - the
uploader queues a job, and the job waits for a worker to claim it. Also missing: the
sweeper for abandoned uploads and the storage-cleanup drain. AI video generation, AI
musicians and training pipelines are out of scope for this repository.
